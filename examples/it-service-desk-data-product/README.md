# IT Service Desk: a worked example

A full AI-Native Data Product: all six modules, Memory with both facets, deployed on Teradata under a `STRICT_SEPARATION` placement standard. It is the end-to-end test of the design, build and review pipeline, and the worked case to read if the normative documents are heavy going.

Everything in this directory is input. Running the example produces a design brief, DDL, a deployed database, and a trust map, and those belong in a product repository of their own. Nothing generated by a run comes back here, which is what keeps a second run comparable to the first.

---

## What the product does

It is the central data product for IT service desk operations, serving four things at once: SLA-breach prediction on open tickets, semantic retrieval of similar past tickets and their resolutions, quality monitoring across the ticket lifecycle, and session continuity for an agent working a multi-step investigation.

Four entities. `Ticket`, `Agent` and `Customer` are `History` entities on the bi-temporal profile. `Category` is a `Reference` entity that carries no history.

## What is supplied

| File | What it is |
|---|---|
| [`ITSD_Reference_Brief.md`](ITSD_Reference_Brief.md) | The fixed input. Intake blocks for each phase, every catalogued decision pre-settled with its reason, the entity and feature models, the physical design, and the deployment sequence. |
| [`ITSD_Object_Placement_Standard.md`](ITSD_Object_Placement_Standard.md) | A conforming placement standard: all eight required sections, `STRICT_SEPARATION`, seven `ITSD_*` databases. The build starter refuses to invent containers, so this is a hard prerequisite. |
| `data/tickets.csv` | 150 tickets, June to July 2026. Open, in-progress, resolved and closed, with nulls on resolution time, closure time, resolution notes and satisfaction score where the lifecycle has not reached them. |
| `data/agents.csv` | 12 agents across three teams, L1 to L3. `email` is `[pii]`. |
| `data/customers.csv` | 20 customers, four tiers, three regions. `contact_name` and `contact_email` are `[pii]`. |
| `data/categories.csv` | 15 categories on two levels: five parents and ten leaves, so the reference hierarchy is real rather than flat. |

The nulls and the hierarchy are there for a reason. A fixture where every column is populated exercises none of the completeness rules, and a flat reference table exercises no parent join.

## What it deliberately exercises

- A recorded departure. `DEC-AUDIT-RETENTION` is settled as `bounded` rather than the advocated `regulatory`, with its reason stated. The reviewer should find that reason in Memory and mark it a deliberate deviation. A run where the reviewer flags it as a defect is a finding about the review skill.
- A partial departure. `DEC-SURROGATE-ALLOCATION` uses `keymap` for the three `History` entities and inline allocation for `Category`.
- Bi-temporal history, chosen because the Prediction module needs point-in-time correctness: ticket reclassifications must not leak into training features.
- `STRICT_SEPARATION` placement, so the access layer's Phase 1.5a implied grants actually matter. Under co-located placement they are empty and the failure they prevent never appears.
- Free text carrying incidental PII in `description` and `resolution_notes`, flagged as a risk in Memory with no runtime masking in this cycle.

## Before you start

You will need Python 3.8 or later for the linters. They are stdlib-only. `jinja2` is needed only if you want to render the DDL templates locally.

You will need a Teradata system you can create databases and roles on. Role creation needs elevated privilege, so confirm it before you begin. The build starter asks you to check this early rather than discover it two phases later:

```sql
SELECT * FROM DBC.AllRightsV WHERE UserName = USER AND AccessRight = 'CG';
```

You will also need the Teradata MCP server connected, for DDL execution, validation runs and review evidence, and a product repository separate from this one, laid out per section 2 of the brief.

One thing to settle first: the brief names Teradata Vantage 17.20, while the Teradata binding in this corpus targets v20.0. Reconcile those against the system you are deploying to before you start, and record the answer as a decision if it differs from the brief.

## Step 0. Generate the skills

`skills/` is gitignored, so a fresh clone has none. All four starters need them.

Run [`prompts/Skill_Conversion_Prompt.md`](../../prompts/Skill_Conversion_Prompt.md) in a conversation with access to this repository, then verify what it produced:

```bash
python tooling/compiler/verify_skills.py
```

It checks that the compression kept everything it was required to keep: every module, decision, invariant and conformance rule, with platform SQL preserved verbatim rather than paraphrased. Fix any problem it reports before running a phase. A skill missing a rule produces a product missing it too, and the run will look like a standards defect.

Regenerate whenever `design/` or `implementation/` changes. On any conflict the repository wins, never the skill.

## Step 1. Set up the product repository

Create the repository and copy the inputs across:

```bash
mkdir -p itsd-data-product/{data,standards,design,build,review,validation,logs}
cp examples/it-service-desk-data-product/data/*.csv          itsd-data-product/data/
cp examples/it-service-desk-data-product/ITSD_Object_Placement_Standard.md \
   itsd-data-product/standards/object_placement.md
```

Add `.env.example` with `TD_HOST`, `TD_USER`, `TD_PASS`. Keep real credentials out of the repository.

## Step 2. Design

Open [`prompts/Design_Data_Product_Starter.md`](../../prompts/Design_Data_Product_Starter.md), paste section 3a of the brief into its Intake section, and start a conversation with the `design` skill loaded.

The agent works module by module, Domain first, and raises the catalogued decisions one at a time. Answer each from section 3b. Do not re-open a settled decision or improve on an answer. The brief is frozen so that the skills are the only thing that varies between runs.

Outputs are `design/design_brief.md` and `design/decisions_log.md`. Validate the brief before going further:

```bash
python tooling/evals/brief_lint.py itsd-data-product/design/design_brief.md
```

It reports unsettled decisions, hard requirements no module in the composition satisfies, invariants the brief never acknowledges, and platform SQL that has no business being there yet. A clean run is the precondition for build. Use `brief_lint` rather than `design_lint`: the latter checks that the standards are well formed and says nothing useful about a product.

Commit: `design: ITServiceDesk design brief and decisions log`

## Step 3. Build

Open [`prompts/Build_Data_Product_Starter.md`](../../prompts/Build_Data_Product_Starter.md) and paste section 4a. The design brief from Step 2 is the input, and the placement standard in `standards/` is a hard prerequisite the agent must read in full before generating any object.

Apply the physical design in section 4b: primary indexes, partitioning, temporal conventions, statistics. Generate `build/00_databases_and_roles.sql` through `build/08_prediction.sql`, plus `deploy.sh` and `teardown.sh`.

Commit the SQL before executing any of it (`build: generate DDL — ITServiceDesk`). Then check it, because two classes of defect are cheap to catch here and expensive to catch on the platform:

```bash
python tooling/validation/design_lint.py design implementation itsd-data-product
```

This reports prohibited temporal column names and any `COMMENT ON` over Teradata's 255-character limit, across `.sql` and `.dcl` files alike. The over-length comment is the one worth pre-empting. `CREATE ROLE` runs before `COMMENT ON ROLE` in the same block, so a rejected comment leaves the role created and undescribed, and the deployment looks like it worked. Keep the `design` and `implementation` paths in the command, because the prohibited-name list is read from the pattern document rather than copied into the linter.

Deploy in the order given in section 4b, committing at each phase boundary per the cadence in section 1:

| Phase | Files | Commit |
|---|---|---|
| 1 + 1.5 | `00` to `03` (databases, roles, Memory, Semantic, access phase 1) | `build: Memory and Semantic deployed` |
| 2 + 2.5 | `04` to `06` (Domain, Observability, access phase 2) | `build: Domain and Observability deployed` |
| 3 | `07` to `08` (Search, Prediction), then `validation/validation.sql` | `build: Search and Prediction deployed; validation passed` |

Test each `CREATE` with `SHOW TABLE` or `EXPLAIN` before executing it. Apply column comments as their own gated step and verify none are missing before starting the next phase. `RichMetadata` is a hard requirement, and a comment block silently skipped after a stalled table creation is the failure mode the standards call out by name.

## Step 4. Review

Open [`prompts/Review_Data_Product_Starter.md`](../../prompts/Review_Data_Product_Starter.md) and paste section 5a. The reviewer reads evidence from the deployed product over MCP rather than from the SQL alone: Semantic for registration completeness, Memory for the recorded decisions, Observability for quality and validation results, `DBC.TablesV` and `DBC.ColumnsV` for metadata coverage.

Module order is Memory, Semantic, Domain, Observability, Search, Prediction. Output `review/trust_map.md` in the format in section 5b, with a severity per finding and an overall confidence rating.

Commit: `review: trust map complete`

## Step 5. Use it

Open [`prompts/Access_Data_Product_Starter.md`](../../prompts/Access_Data_Product_Starter.md) against the deployed product. This step tells you whether any of the preceding work paid off. An agent that has never seen the design should be able to orient itself from the Semantic map, find the right entrypoint, and answer a question about ticket SLA performance without being told the schema.

## Re-running

```bash
cd itsd-data-product && ./teardown.sh && ./deploy.sh
```

Both scripts are generated during Build and committed before any SQL executes, so a complete redeploy on an empty system needs no agent involvement. That is the check on whether the build is genuinely reproducible or merely happened to work once.

## What to record after a run

The run is a test, so its output is not only the product. For each defect, decide which of three things it is, because the fix differs.

A standards defect means the corpus permitted something it should not, or failed to say something a builder needed. Fix `design/` or `implementation/`, add a check under `tooling/validation/` where one could have caught it, and regenerate the skills.

A skill defect means the corpus says it and the skill lost it in compression. `verify_skills.py` catches the mechanical cases. The rest show up as an agent that never applies a rule it was never given. Regenerate, and if it recurs, the conversion prompt needs the fix.

A fixture defect means the brief or the placement standard is wrong. Fix it between cycles, never mid-run, and note that the affected run is not comparable to the ones before it.

## What the brief settles, and what it leaves to the standards

The brief pre-settles product decisions and nothing else. Where a name belongs to a module or a pattern, the brief points at it rather than restating it, because a fixture that restates a name is a fixture that can disagree with the standard it is meant to test.

So the brief settles the entity model, the feature register, the quality dimensions and thresholds, the physical design, and the answer to each catalogued decision. It does not settle the temporal column names, the module catalogue entities, or the role model. Those come from the [temporal pattern](../../design/patterns/temporal-lifecycle-metadata.md), the module documents, and the [access-layer pattern](../../design/patterns/access-layer.md).

Two places where the boundary is easy to misread are worth calling out.

Source columns are not product columns. The feature register's Source column names fields in `tickets.csv`, quoted as `tickets.csv:created_at` to keep it obvious. They are inputs being read, not columns being defined. The product's own audit column is `created_dts`, and the linter's TLM-04 check applies to the generated DDL rather than to a description of a source file.

`Category` earns its `effective_date` and `expiration_date` from its declared profile. TLM-04 permits those two names on a `CURRENT_STATE` entity and prohibits them everywhere else, and the permission turns on the profile the entity declares in the Semantic entity metadata, not on what kind of thing the table holds. Category declares `CURRENT_STATE`, departing from the `SCD2_HISTORY` default for a `Reference` entity, and that departure is itself recorded as a design decision. An entity registered with no profile cannot claim the exception whatever its columns are called.

## Deliberate departures

There are two, both recorded with reasons, and both expected to survive review as deviations rather than defects:

| Departure | From | Why |
|---|---|---|
| `DEC-AUDIT-RETENTION` = `bounded` | Advocated `regulatory` | No statutory retention obligation in this deployment context. A 3-year window covers operational investigation and pattern depth. |
| `Category` declares `CURRENT_STATE` | `SCD2_HISTORY`, the `Reference` default | A small internal taxonomy whose labels are not reworded in service. No ticket needs to resolve a category name as at its creation date. |

A reviewer that flags either as an oversight is reporting a defect in the review skill, not in the product. Anything else in the brief that conflicts with a standard is a fixture defect: fix it between cycles, and note that the affected run is not comparable to the ones before it.

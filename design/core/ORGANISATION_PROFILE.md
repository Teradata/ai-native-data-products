# Organisation Profile Standard

## 1. Purpose

An **organisation profile** is how an organisation configures the standards for its own environment: where objects are placed, what they are called, which principals reach them, how its classification scheme maps onto the design's sensitivity markers, what retention it permits, how its environments differ, and which existing structures a product adopts. It is written once per organisation and platform and reused by every product built there, so no design specification, standard or template has to encode one organisation's conventions ([Platform Implementation Authoring Standard](IMPLEMENTATION_AUTHORING.md) §4).

A profile is a markdown document whose rules live in notation blocks, as in a [design specification](DESIGN_SPECIFICATION.md). The build-context resolver, `tooling/build/build_context.py`, reads the tables in this document, validates a profile against them, and executes its rules; a table here is the rule, not a description of it. Prose in a profile explains its choices and is never read by a build.

**One profile per platform.** A profile targets one platform. An organisation building on two platforms keeps two profiles; naming and classification policy may be identical in both.

**A profile is the organisation's object-placement implementation.** Its first eight sections carry the eight required sections of the [object-placement pattern](../patterns/object-placement.md), under the headings that pattern requires, with their rules stated in blocks the resolver executes rather than in prose an agent interprets.

| `Classification` | yes | `Classification` |
| `Retention` | no | `Retention` |
| `Environments` | yes | `Environments` |
| `Adoption` | no | `Adoption` |
| `Catalogue` | no | `Catalogue` |
| `Binding Settings` | no | `Settings` |
| `Storage Section 1. Storage Platform Declaration` | no | `Storage` |
| `Storage Section 2. Path Model` | no | `Paths` |
| `Storage Section 3. Path Derivation Pattern` | no | - |
| `Storage Section 4. File Format and Encoding` | no | `Files` |
| `Storage Section 5. Partition Strategy` | no | `Partitioning` |
| `Storage Section 6. Retention and Lifecycle` | no | `Lifecycle` |
| `Storage Section 7. Access Model` | no | `StorageAccess` |
| `Storage Section 8. Validation Procedure` | no | - |

Section 8 states that the placement validation procedure is generated by the platform binding from this profile and run after each deployment phase, halting on failure. It needs no block. The implied grants a separation policy makes necessary are likewise computed by the binding from the resolved placement, never declared by hand.

The eight `Storage Section` headings are the [physical-storage pattern](../patterns/physical-storage.md)'s required sections, for an organisation that keeps product data in object storage. They are present together or not at all; a profile without them declares that no product data is held in object storage. Storage Section 3 is stated by the `Paths:` block's derivation, and Storage Section 8 is generated by the binding, as for placement.

## 3. Frontmatter

| Key | Required | Type | Value |
|---|---|---|---|

## 4. Templates

Names are written as templates: literal text with `{variable}` placeholders, each optionally followed by filters, as in `{entity|snake}`. Only these variables and filters exist.

| Variable | Value |
|---|---|
| `product_code` | The specification's `product_code`. |
| `product` | The specification's `product`. |
| `module` | The module anchor the object belongs to; in a `Containers:` template, the container's own key. |
| `entity` | The entity name, as the specification writes it. |
| `attribute` | The attribute name, as the specification writes it. |
| `container` | A container name, already resolved. |
| `environment` | The lifecycle phase being built. |
| `bucket` | A bucket name, already resolved (storage paths only). |
| `object` | An object name, already resolved (storage paths only). |

| Filter | Effect |
|---|---|
| `lower` | Lower case. |
| `upper` | Upper case. |
| `snake` | `TicketFeatureSet` becomes `ticket_feature_set`. |
| `pascal` | `ticket_feature_set` becomes `TicketFeatureSet`. |
| `abbrev` | A module anchor becomes its abbreviation from `Naming:` `Abbreviations`. |

## 5. Object roles

Every object a build creates has one of these roles. A naming template and a placement rule exist for each role marked required.

| Role | Required | Created for |
|---|---|---|
| `table` | yes | Each persisted entity: the specification's own and the standard-owned relations of included modules. |
| `base_view` | yes | The governed one-to-one view over a table. |
| `consumer_view` | yes | The access-layer view consumers are granted. |
| `procedure` | no | A stored procedure a binding emits. |
| `function` | no | A user-defined function a binding emits. |

## 6. Blocks

Each block opens with `<Block>: -` in a fenced code block. Fields are indented two spaces; a field of type `templates`, `mappings` or `examples` puts its lines below it, indented four. Field types are those of the [Design Specification Standard](DESIGN_SPECIFICATION.md) §2, plus `template`, `templates` (lines `<key>: <template>`), `mappings` (lines `<key>: <value>`), `principal` (`create <template>`, or `existing <name>` to bind an existing principal) `examples` (lines `- <role> <module> <entity> [<Kind>] -> <container>.<object>`, where the kind is given when a naming template depends on it) and `path-examples` (the same, ending `-> <path>`).

### 6.1 `Platform:`

| Field | Required | Type | Value |
|---|---|---|---|
| `Container term` | yes | text | The platform's word for a container. |
| `Principal term` | yes | text | The platform's word for an access principal. |
| `Namespace` | yes | enum | `flat` or `hierarchical`. |
| `Max name length` | yes | integer | The longest container or object name allowed. |
| `Name characters` | yes | text | The characters a name may use, in words. |
| `Reserved words` | no | terms | Names no container or object may take. |

### 6.2 `Containers:`

Each field is a container key and its name template. A key is a module anchor, `access` for the access layer, or any other key a placement rule routes to (a shared registry container, say). Every included module must reach a container through the placement rules. A line may end `in <key>` to place the container under a parent container; a parent organises containers and holds no objects, and a placement rule may not route to one.

| Field | Required | Type | Value |
|---|---|---|---|
| `*` | yes | template | One line per container. |

### 6.3 `Naming:`

| Field | Required | Type | Value |
|---|---|---|---|
| `Objects` | yes | templates | One line per object role, as `<role>`, optionally followed by a module anchor, an entity kind, or both (`table domain History`), to name a narrower set differently. The most specific matching line wins. |
| `Attributes` | no | template | Physical attribute names. Defaults to `{attribute}`. |
| `Standard names` | no | mappings | Physical names for standard-owned logical names, as `<logical>: <physical>`. One-to-one, and never onto a name another standard-owned name or a specification attribute already holds; unlisted names stay as written. |
| `Abbreviations` | no | mappings | Module abbreviations for the `abbrev` filter, as `<module>: <abbreviation>`. |
| `Graph key` | no | template | The graph key a product with the `observability:graph-lineage` facet registers. Required when any product enables that facet. |

### 6.4 `Placement:`

| Field | Required | Type | Value |
|---|---|---|---|
| `Rules` | yes | mappings | One line per object role, or per standard-owned relation, giving the container key: a key from `Containers:`, or `module` for the object's own module container. A role may be narrowed by a classification, as `<role> <class>`, to route objects holding data of that class (an entity's class is its most sensitive attribute's) to their own container. |

### 6.5 `Separation:`

| Field | Required | Type | Value |
|---|---|---|---|
| `Policy` | yes | enum | `STRICT_SEPARATION`, `TYPE_GROUPED`, `CO_LOCATED` or `CUSTOM`. |
| `Object naming` | yes | enum | `container-discriminated` or `name-discriminated`. |
| `Exceptions` | no | text | Any stated exception and why. |

### 6.6 `Derivation:`

| Field | Required | Type | Value |
|---|---|---|---|
| `Product code` | yes | text | The product code the examples are worked for. |
| `Examples` | yes | examples | At least three worked derivations. The resolver re-derives each and rejects the profile if any disagrees. |

### 6.7 `Principals:`

| Field | Required | Type | Value |
|---|---|---|---|
| `ROLE_READ` | yes | principal | The principal for the read tier. |
| `ROLE_AGENT` | yes | principal | The principal for the agent tier. |
| `ROLE_ADMIN` | yes | principal | The principal for the admin tier. |
| `Grant level` | yes | enum | `container` or `object`. |

### 6.8 `Classification:`

| Field | Required | Type | Value |
|---|---|---|---|
| `Scheme` | yes | terms | The organisation's classes, least to most sensitive. |
| `Default` | yes | text | The class of an attribute with no marker. |
| `Markers` | yes | mappings | Each specification sensitivity marker (`pii`, `pii-incidental`) and its class. |
| `Protection` | yes | mappings | Each class and its protection: `none`, or `mask` or `exclude` followed by `for` and the tiers it applies to. |

### 6.9 `Retention:`

Bounds a specification's `Retention:` block must satisfy for audit and execution records: the Observability module's entities. A duration outside a bound fails resolution. `life of product`, which `INV-OBS-004` requires of definitional lineage, is outside the bounds by definition.

| Field | Required | Type | Value |
|---|---|---|---|
| `Audit minimum` | no | duration | Shortest retention for audit and execution records. |
| `Audit maximum` | no | duration | Longest retention for audit and execution records. |
| `Personal data maximum` | no | duration | Longest retention for any entity holding records about people: Memory's runtime entities, and any entity with an attribute the profile classifies through the `pii` marker. |

### 6.10 `Environments:`

| Field | Required | Type | Value |
|---|---|---|---|
| `Phases` | yes | terms | The lifecycle phases, in promotion order. |
| `Isolation` | yes | enum | `system` or `container`. With `system` each phase is a separate system and names are identical; with `container` phases share a system and container names differ. |
| `Container template` | no | template | With `container` isolation, how a phase changes a container name, using `{container}` and `{environment}`. Object names never change (`INV-MASTER-006`). |

### 6.11 `Adoption:`

Existing structures a product uses instead of creating its own. A binding honours an adoption or reports it as unsupported; it never creates a duplicate.

| Field | Required | Type | Value |
|---|---|---|---|
| `Containers` | no | mappings | Container keys that already exist, as `<key>: <existing name>`. |
| `Entities` | no | mappings | Specification entities bound to existing objects, as `<product_code>.<Entity>: <container>.<object>`. |
| `Column aliases` | no | mappings | For an adopted entity whose columns predate the standard, the existing column for each logical attribute, as `<product_code>.<Entity>.<attribute>: <column>`. The binding presents the canonical name over it. |
| `Allocator` | no | text | The organisation's existing surrogate-key allocator, which an `external-allocator` choice uses. Required when any product chooses it. |

### 6.12 `Catalogue:`

How this organisation's catalogue reads products, under the [catalogue-interface pattern](../patterns/catalogue-interface.md).

| Field | Required | Type | Value |
|---|---|---|---|
| `States` | no | terms | The lifecycle state vocabulary, when the pattern's advocated states do not fit the organisation's governance process. |
| `Layers` | no | mappings | The layer code the catalogue shows for each object role, as `<role>: <code>`. |
| `Projection` | yes | enum | `release` or `live`: whether the interface feed is projected at release or read live. |

### 6.13 Storage blocks

#### `Storage:`

| Field | Required | Type | Value |
|---|---|---|---|
| `Object store` | yes | text | The object-store service and any region constraint. |
| `Table format` | yes | text | The open table format, or `raw files`. |
| `Scope` | yes | enum | `all` or `declared`: whether every table is in object storage, or only those `Paths:` routes. |
| `Excluded` | no | terms | Object roles or standard-owned relations kept out of object storage. |

#### `Paths:`

| Field | Required | Type | Value |
|---|---|---|---|
| `Buckets` | yes | templates | One line per bucket key and its name template. |
| `Bucket rules` | yes | mappings | One line per object role, optionally narrowed by a classification, giving the bucket key. |
| `Path` | yes | template | The object path, using `{bucket}`, `{container}`, `{object}`, `{environment}` and the product variables. |
| `Examples` | yes | path-examples | At least three worked derivations. The resolver re-derives each and rejects the profile if any disagrees. |

#### `Files:`

| Field | Required | Type | Value |
|---|---|---|---|
| `Format` | yes | text | The default file format for persistent tables. |
| `Compression` | yes | text | The default compression. |
| `Schema evolution` | yes | text | What changes are permitted in place and what requires recreation. |
| `Prohibited` | no | terms | Formats never used for persistent tables. |

#### `Partitioning:`

| Field | Required | Type | Value |
|---|---|---|---|
| `Model` | yes | enum | `hidden`, `hive` or `none`. |
| `Rule` | yes | text | How partition keys are chosen. |
| `Maximum` | no | integer | The most partition keys a table may take. |

#### `Lifecycle:`

| Field | Required | Type | Value |
|---|---|---|---|
| `Snapshot retention` | yes | duration | How long table snapshots are kept. |
| `Orphan cleanup` | yes | duration | Age after which unreferenced files are removed. |
| `Tiering` | no | text | Storage tiering rules. |

#### `StorageAccess:`

Physical access never exceeds logical access.

| Field | Required | Type | Value |
|---|---|---|---|
| `Principals` | yes | mappings | The physical principal for each access tier, as `<tier>: <template>`. |
| `Bucket policy` | yes | text | How bucket policies are structured. |

### 6.14 `Settings:`

Values for binding settings the platform's profile declares configurable. A setting the binding does not declare fails the build with a reported gap.

| Field | Required | Type | Value |
|---|---|---|---|
| `*` | yes | text | One line per setting. |

## 7. What the resolver checks

The resolver rejects a profile, before any template renders, when:

- a required heading or block is missing, or a block carries a field outside its table or a value invalid for its type;
- a template uses a variable or filter outside section 4, or a placement rule names a container key that does not exist;
- a required object role has no naming template or placement rule;
- a standard-name mapping is not one-to-one;
- a derivation example disagrees with what the profile derives;
- a resolved name exceeds the platform's length, uses a reserved word, or collides with another object in the same container;
- a container's parent is not a container key, a parent is routed to, or the parents form a cycle;
- a placement or bucket rule names a class outside the classification scheme, or the `abbrev` filter meets a module with no abbreviation;
- some but not all of the `Storage Section` headings are present, or a storage derivation example disagrees with what the profile derives;
- a product chooses `external-allocator` and the profile names no `Allocator`, or enables graph lineage and the profile has no `Graph key`.

# Compatibility policy and release index

This directory holds the release bundle: the consumer contract of a deployed AI-Native Data
Product, versioned with the standard. It is not a module. Nothing here is deployed; the bundle
describes what a deployment implements and what an agent reading it can rely on.

Each `vX.Y.Z/` directory is generated by `tooling/release/build_release.py` from the repository
and is checked for staleness by `tooling/release/tests`. Do not edit generated files. This
document and `migrations/` are authored.

## Reading a deployment

A deployment declares the standard version it implements in `StandardDeclaration`, and the manifest
view repeats it as its last column, `standard_version`. A declaration is an assertion, not evidence.
Evidence is the trust map.

| Question | Where an agent looks |
|---|---|
| Which release does this deployment claim? | The manifest's `standard_version` |
| Which modules and patterns, on which platform? | The `StandardDeclaration` consumer view |
| What can I rely on in that release? | `release/vX.Y.Z/contract.json` for that version |
| What changed since the release I know? | The rows below and `migrations/` |

## Versioning

One semantic version covers the whole standard, held in the root `VERSION` file. A tag must equal
`v` plus that value.

| Bump | When |
|---|---|
| Major | A consumer-facing surface changes incompatibly: a metadata relation, attribute or discovery view is removed or renamed, an attribute changes meaning or type, a discovery role changes the object it names, or the rules for identity, keys or join order change |
| Minor | A surface is added without changing an existing one: a new relation, view or attribute, a new check, a new optional capability |
| Patch | Comment text, documentation or tooling changes that alter no surface |

## What is stable

A consumer may rely on these across minor and patch releases:

- **Logical identities.** Entities, access objects and composites are identified by the grammar in
  `contract.json` (`identity_grammar`): `module.entity`, `module.entity:surface`, `module:object` and
  `composite:name`. An identity contains no container, product prefix or object-type affix and does
  not change when a container is renamed or the design is deployed with different placement. The
  physical container and object name are separate columns.
- **Ordered groups are rows.** A key is the ordered rows of `KeyColumn`; a relationship is a join group
  whose column pairs are the ordered rows of `RelationshipColumn`; a consumer view's output columns are
  the rows of `AccessColumn`. Ordinals run 1 to n without gaps. No platform stores a group as a list,
  an array or a delimited string.
- **Join paths are rows.** `RelationshipPaths` returns one row per step and key position, with the
  columns and order listed in `contract.json`. A path has at most four steps and visits no entity
  twice. The consumer assembles the join; no join string is part of the contract.
- **Discovery roles.** The roles in `contract.json` and the views they name, with their columns and the
  order in which an agent reads them.
- **Standard relations and views.** The names and types of each relation in `contract.json`; the columns
  of each discovery view. New columns are added only at the end of a view. Column meanings are in
  `design/modules/semantic.md`.
- **Comments exist.** Every product container (where the platform allows), table, view, routine and
  column carries a comment (the `comment-coverage` check). The wording of a comment is not stable.

## Known limitations in 2.0.0

| Area | Limitation today |
|---|---|
| Physical keys | A key is described as ordered columns, but the Domain module still allocates one surrogate column per entity. A composite natural key is registered as ordered rows; this is metadata, not a change to how rows are keyed |
| Bare references to composite identities | A bare `[-> Target]` carries one source column. Where the target's identity has several columns it pairs the first and the build reports the rest as a gap. Name the target attributes (`[-> Target.attribute]`) to declare the whole join |
| Generated mappings | Bindings generate `PASSTHROUGH` access columns for consumer views over entities. `RENAMED` and `DERIVED` mappings and composite access objects are not generated by any binding |
| Discovery views | The standard-owned discovery views are consumer views over no registered entity. Their columns are published here, not as `AccessColumn` rows |
| Declaration | A declaration is an assertion. Nothing verifies it against the deployment |
| Column meanings | The release bundle lists the standard relations' attributes by name and type; their meanings are in the design |

## Platform differences a consumer may meet

The contract is the same on every platform: identity grammar, ordered-group rows and path columns.

| Platform | Difference |
|---|---|
| duckdb | Schemas cannot be commented, so the comment-coverage sweep covers tables, views, columns, sequences and macros |
| teradata | The point-in-time surface is a view, not a callable function (declared in the binding's gaps) |

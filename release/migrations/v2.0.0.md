# Migration note: 2.0.0

Type: **major, breaking.** The metadata an agent reads from a deployed product changes shape. Business
data tables, their keys and their temporal mechanics do not change. This release also carries the
content of a prepared 1.1.0 that was never tagged: the release bundle, the declared standard version
and comment coverage.

## What changed

### Breaking

| Change | Detail |
|---|---|
| Logical identities | An entity is `module.entity` (`domain.ticket`); an access object is `module.entity:base`, `:governed`, `:current`, `:history`, `module:object` or `composite:name`. Identities no longer contain a container. Every attribute that held an entity or object identity now holds the logical form |
| Keys | `EntityMetadata` loses `surrogate_key_column` and `natural_key_column`. Keys are rows in the new `KeyDefinition` and `KeyColumn`. A composite natural key, which 1.x stored as one comma-joined string, is now its ordered rows |
| Relationships | `TableRelationship` loses its container, table and column attributes and names the logical `source_entity` and `target_entity`. The column pairs are rows in the new `RelationshipColumn`; the relationship is the join group |
| Composites | `AccessComposition.join_path` is removed. A member names `via_relationship_id` and `via_direction` |
| Paths | `RelationshipPaths` returns rows, not strings, with the columns `path_id, origin_entity, destination_entity, hop_count, hop, key_ordinal, from_entity, from_column, to_entity, to_column, relationship_id, direction`. The old `join_path` string and the `hops` column are gone on every platform |
| Access objects | `AccessObject` gains `object_identity`. `represents_entity` and `resolves_to_object` hold logical identities |

### Additive

| Change | Detail |
|---|---|
| Access-column mappings | New `AccessColumn`: one row per output column of a consumer view over an entity, with its source entity and column and a mapping kind |
| Declared standard version | New `StandardDeclaration`; `standard_version` is the last column of the manifest view |
| Release bundle | `release/v2.0.0/` publishes the contract, bindings, examples and conformance checks |
| Conformance checks | The five `contract` checks (`INV-SEMANTIC-016` to `020`) and the `comment-coverage` check on all three platforms |
| Comment parity | Views, view columns, functions or macros, sequences and (where the platform allows) schemas carry comments in rendered products |

## The old-to-new identity rule

| Old | New |
|---|---|
| Entity named by its business name or `schema.table` | `module.entity`: the module anchor, a dot, the logical name in snake_case (`ValidationRun` becomes `validation_run`) |
| Access object named by `container.object` | `module.entity:surface` by the object's role (table `base`, base view `governed`, consumer view `current`, point-in-time object `history`) |

The container and object name remain in their own columns. Every attribute that held an identity takes
the same rewrite.

## What a deployment must do

There is no migration script. Metadata is established by the registration step, so a 1.x deployment
re-registers against the 2.0.0 relations.

| Step | Action |
|---|---|
| 1 | Create the new relations (`KeyDefinition`, `KeyColumn`, `RelationshipColumn`, `AccessColumn`, `StandardDeclaration`), drop the removed attributes, add the new ones, and replace the discovery views |
| 2 | Re-run registration so every identity uses the grammar and the new relations are populated |
| 3 | Rewrite authored rows that reference identities (metrics, synonyms) with the rule above, or re-capture them from the design |
| 4 | Run the five `contract` checks and `comment-coverage`; every query returns zero rows |

## What an agent should do

Read the manifest's `standard_version`. When it is `2.x`, follow the rows described above. When it is null
or the column is absent, the deployment is 1.x: read the 1.x surface and do not assume keys, identities or
paths follow this release.

To join along a path in 2.x, take the rows of one `path_id`, group them by `hop` in ascending order, and
within a hop join the `from_entity` to the `to_entity` on every `from_column = to_column` pair, ordered by
`key_ordinal`. Resolve each identity to an object through `AccessObject` before issuing SQL.

## Execution evidence

| Platform | Evidence |
|---|---|
| duckdb | Reference products deployed and every rendered check run in the test suite, including a mutation test for each contract check and the coverage check, a composite natural key, a composite join and the declaration |
| postgres | Templates render and share registration with DuckDB. The engine tests are the same and need `POSTGRES_TEST_DSN`; they were not run when this note was written |
| teradata | Templates render under strict undefined variables and pass the repository's validation suite. The DDL, views and checks have not been run on a Teradata system |

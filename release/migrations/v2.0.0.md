# Migration note: 2.0.0

Type: **major, breaking.** The metadata an agent reads from a deployed product changes shape. Business
data tables, their keys and their temporal mechanics do not change. This release also carries the
content of a prepared 1.1.0 that was never tagged: the release bundle, the declared standard version
and comment coverage.

## What changed

### Breaking

| Change | Detail |
|---|---|
| Logical identities | An entity is `module.entity` (`domain.ticket`); an access object is `module.entity:base`, `module.entity:current`, `module:object` or `composite:name`. Identities no longer contain a container. Every column that held an entity or object identity now holds the logical form |
| Keys | `entity_metadata` loses `surrogate_key_column` and `natural_key_column`. Keys are rows in the new `key_definition` and `key_column` |
| Relationships | `table_relationship` loses its column pair (Teradata also loses its container and table columns). The pairs are rows in the new `relationship_column`; the relationship is the join group |
| Composites | `access_composition.join_path` is removed. A member names `via_relationship_id` and `via_direction`; `member_seq` orders the members |
| Paths | `relationship_edges` and `relationship_paths` are rows, not strings. `relationship_paths` has the columns `path_id, origin_entity, destination_entity, hop_count, hop, key_ordinal, from_entity, from_column, to_entity, to_column, relationship_id, direction`. The old `join_path` and `path_joins` strings are gone on every platform |
| Postgres, DuckDB | `access_object` gains `container_name` and `object_name`; `data_product_orientation` and the manifest carry `container_name` and `object_name` in place of `object_identity` |
| Teradata | The views `v_relationship_paths` and `v_access_relationship_paths` are renamed `relationship_paths` and `access_relationship_paths` |

### Additive

| Change | Detail |
|---|---|
| Access-column mappings | New `access_column`: one row per output column of an access object, with its source entity and column and a mapping kind |
| Declared standard version | New `standard_declaration` and `v_standard_declaration`; `data_product_manifest.standard_version` is its last column |
| Release bundle | `release/v2.0.0/` publishes the contract, bindings, examples and conformance checks |
| Conformance checks | `INV-SEMANTIC-016` to `020` on all three platforms, and the `comment-coverage` sweep on all three |
| Comment parity | Views, view columns, functions or macros, sequences and (where the platform allows) schemas now carry comments in rendered products |

## The old-to-new identity rule

| Platform | Old | New |
|---|---|---|
| postgres, duckdb | Entity `itsd_domain.ticket` | `domain.ticket`: the module anchor, a dot, the table name |
| postgres, duckdb | Base object `itsd_domain.ticket`; consumer view `itsd_access.v_ticket` | `domain.ticket:base`; `domain.ticket:current` |
| teradata | Entity `Party` (a business name) | `domain.party`: the lower-case module anchor, a dot, the logical name in snake_case (`ValidationRun` becomes `validation_run`) |
| teradata | Access or primary object `Database.Object` | By the grammar above; the location stays in `database_name` and `object_name` |

Every reference column (`source_entity`, `target_entity`, `member_entity`, `represents_entity`,
`resolves_to_object`, and the entity or object names held by metrics and synonyms) takes the same
rewrite. `column_metadata` and `column_catalogue` stay keyed by physical location on Teradata.

## What a deployment must do

There is no migration script. Metadata is established by the registration step, so a 1.x deployment
re-registers against the 2.0.0 tables.

| Step | Action |
|---|---|
| 1 | Apply the DDL delta: create the new tables (`key_definition`, `key_column`, `relationship_column`, `access_column`, `standard_declaration`), drop the removed columns, add the new ones, and replace the discovery views |
| 2 | Re-run registration so every identity uses the grammar and the new tables are populated |
| 3 | Rewrite authored rows that reference identities (metrics, synonyms) with the rule above, or re-capture them from the design |
| 4 | Run `INV-SEMANTIC-016` to `020` and the comment-coverage sweep; every query returns zero rows |

**Teradata registration.** The Teradata templates create the new tables, views and checks. The
builder step that populates `key_definition`, `key_column`, `relationship_column`, `access_column` and
`standard_declaration` is not part of the repository templates. Until it is run, `INV-SEMANTIC-017`,
`018` and `019` report every entity, relationship and consumable object, which is the correct signal that
the metadata is not yet registered.

## What an agent should do

Read `data_product_manifest.standard_version`. When it is `2.x`, follow the rows described above. When it
is null or the column is absent, the deployment is 1.x: read the 1.x surface and do not assume keys,
identities or paths follow this release.

To join along a path in 2.x, take the rows of one `path_id`, group them by `hop` in ascending order, and
within a hop join the `from_entity` to the `to_entity` on every `from_column = to_column` pair, ordered by
`key_ordinal`. Resolve each identity to an object through `access_object` before issuing SQL.

## Execution evidence

| Platform | Evidence |
|---|---|
| duckdb | Reference products deployed and every check run in the test suite, including a mutation test for each new check and a composite relationship |
| postgres | Rendered and audited statically in tests. The database-backed tests are written and require `POSTGRES_TEST_DSN`; they were not run when this note was written |
| teradata | Templates render under strict undefined variables and pass the repository's validation suite. The DDL, views and checks have not been run on a Teradata system |

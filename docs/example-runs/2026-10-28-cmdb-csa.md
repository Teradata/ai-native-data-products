# First run: IT Asset Configuration and Customer Service Agreements

Run 2026-10-28. Two new example products, designed, built and reviewed against the standards as
they stand on `feat/80-toml-and-generator`, as the first step towards three products used
together. This report is the run's record: what was built, the trust map for each product, and
what the run found. It is not part of the skill package (`docs/` is export-ignored).

| Product | Code | Composition | Built on | Seed data |
|---|---|---|---|---|
| [IT Asset Configuration](../../examples/it-asset-configuration-data-product/) | `CMDB` | Traditional (Domain, Semantic, Observability, Memory documentation) | PostgreSQL 16.11 | 235 items, 300 dependencies, 161 ticket links |
| [Customer Service Agreements](../../examples/customer-service-agreements-data-product/) | `CSA` | AI-Native without runtime Memory | DuckDB 2.0.0 | 21 customers (23 versions), 48 contracts, 184 terms, 9 credits |
| [IT Service Desk](../../examples/it-service-desk-data-product/) | `ITSD` | AI-Native | Teradata (already) | unchanged |

All three share one organisation profile (`config/`) and one set of customer numbers. Both new
seed data sets are generated from ITSD's files, so every customer and ticket number they hold
exists there, apart from the deliberate cases in the CSA README.

## Findings

Each finding is sorted by where its fix belongs, as the examples README asks.

### Standards

- **S1. Relationship identity contradicts itself.** Domain §3.3's template allocates a
  Relationship `inline` with a natural key only ("its identity is the pair of references"), but
  the Design Specification Standard §3.3 and `spec_lint` require both a surrogate and a natural
  key under `inline`. Both CMDB relationships failed lint until given a surrogate. Fix one or
  the other; a relationship nothing references arguably needs no surrogate.
- **S2. No notion of "now" in the expression vocabulary.** "Items past end of support" and
  "contracts ending in the next 90 days" are the products' headline questions, and neither can be
  a `Metric`: no function yields the current date, so no filter can compare to it.
- **S3. `composition` is free text.** CSA declares `custom`; nothing checks it against the Master
  Design's presets, and a free composition has no name to declare.
- **S4. `spec_lint` accepts a History entity with no current or deleted flag.** `Contract` was
  written without them and linted clean; every other versioned entity declares both.

### Bindings and tooling

- **T1. Quality functions not rendered on any binding:** `integrity`, `freshness` (known) and now
  `uniqueness`. Every CMDB quality rule that would find the planted defects is a gap.
- **T2. Feature functions not rendered on any binding:** `as_of` (known), `sum_related`,
  `count_related`, `days_since_last`. Half of CSA's renewal features cannot be built.
- **T3. A trust map can say `strong` over an empty module.** CSA's prediction module publishes
  `pass`/`strong` with no feature rows and no predictions, because its checks are structural.
  A consumer reading the map is told to trust a model that has never scored.
- **T4. Acronyms snake-case badly.** `{entity|snake}` turned `CIType` into `citype`; the example
  renamed the entity to `ItemType`.
- **T5. Release coverage credits the shared configuration to ITSD alone.** The two new examples
  list no platforms in `release/v2.0.0/examples.json`. Whether they should, before they are in
  the conformance runs, is open.

### Pipeline (no home yet)

- **P1. No loader.** The corpus builds structure; loading seed data is "the product's own
  pipeline", so each run writes its own. This run wrote one modelled on the binding tests'
  `load_itsd`: keymap allocation through the dialect, inline surrogates read back, references
  by natural key, versions closed by the next `valid_from`.
- **P2. No embedding or feature pipeline.** Nothing generates embeddings with the declared
  model, populates a feature group, or scores a model. The `Embed` capability is bound to a
  column type, not to anything that computes a vector.

### Fixture

- **F1.** ITSD's `tickets.csv` has a replacement character in TKT-00011's subject: an encoding
  defect from an earlier edit.

## What this means for step 3

These are the inputs for the discussion on managing products together and consuming them for
analytics, recorded without proposing a fix.

- **X1. No product exposes its business keys to consumers.** Every consumer view carries the
  surrogate only, and the keymaps are granted to no consumer tier, on PostgreSQL and DuckDB
  alike (ITSD's own views were checked as rendered). CMDB holds `CUST-007` and `TKT-00042`;
  ITSD's views expose only the surrogates ITSD's own keymaps allocated for them. No consumer can
  join the two, so `NaturalKeyLookup` exists only for the admin
  tier.
- **X2. No reference to another product's entity.** Both products hold the other product's
  natural key as unenforced `ShortText` (`DD-DOMAIN-004` in each). Because it is not a
  reference, it is not in the relationship catalogue, `RelationshipPaths` or the lineage graph:
  a knowledge graph built from each product's Semantic store would show three disconnected
  islands.
- **X3. Shared entities and system of record.** `Customer` exists in ITSD and CSA under the same
  numbers, and they disagree (two tiers, a name, a start date, a customer only CSA has). CSA
  records itself as the system of record for tier in a `Decision:` block: prose, which nothing
  reads.
- **X4. Cross-product features and checks are impossible by design.** CSA's renewal model cannot
  use ITSD's breach history (`DD-PRED-002`), and no product can check another's keys
  (`DD-OBS-002` in each). Each product's trust map is clean while TKT-00999 is credited and does
  not exist.
- **X5. Each product's trust map says nothing about the others.** Products are self-contained
  (`INV-MASTER-003`); the one organisation-level store, the catalogue registry, had its templates
  retired on 2026-10-23.
- **X6. Three engines, no shared query surface.** ITSD on Teradata, CMDB on PostgreSQL and CSA in
  a DuckDB file: an analysis across them needs federation, by an agent or an engine.
- **X7. The contracted SLA and the service desk's SLA differ.** ITSD flags breaches against a flat
  target per priority; CSA's contracts set resolution hours by tier. The two products disagree
  on what breached, which is the analytical question the three products exist to answer.

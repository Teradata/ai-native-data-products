# Metadata contract 2.0.0: design

Status: approved in conversation 2026-10-14; revised the same day to sit on PR 77's build-context
architecture, which supersedes the per-binding inputs this design was first written against.

## Purpose

Sub-project **B**. [The release contract design](2026-10-14-release-contract-design.md) (A) published
a versioned bundle and a declared standard version, and listed four limitations of the metadata an
agent reads from a deployed product. B removes them in one breaking release, **2.0.0**:

| Limitation in 1.x | Resolution in 2.0.0 |
|---|---|
| Object identity embeds the physical container | Logical, placement-independent identities; location in separate columns |
| One surrogate and one natural key column per entity (a composite natural key was a comma-joined string) | Key definitions with ordered key columns |
| One column pair per relationship, no grouping | A relationship is a join group of ordered column pairs |
| Join paths are concatenated strings that differ by platform | Paths are rows with hop and key position; the agent assembles the SQL |
| No record of where an access-view column comes from | One mapping row per output column of a consumer view |

The prepared, untagged 1.1.0 release (declaration, comment coverage, release bundle) folds into
2.0.0. 1.1.0 is never tagged.

## Where this sits

PR 77 gives every binding one input, the build context, resolved from the design specification, an
organisation profile and the binding's own declarations. The Semantic relations are defined in
`design/modules/semantic.md` and placed by `tooling/build/build_context.py`; templates read the context
and write rows by logical attribute name. This design is expressed in those terms:

- the design defines the new relations, so every platform creates them from the same definitions;
- the resolver derives the identities, keys, relationship pairs and consumer-view columns once, for
  every binding;
- each binding writes the rows, creates the views and declares the checks.

## Decisions

| Decision | Choice |
|---|---|
| Scope | Metadata contract only. The Domain module's key allocation, keymaps and temporal mechanics do not change |
| Platforms | All three: Teradata, Postgres, DuckDB, each a set of Jinja templates over the build context |
| Identity | Logical and placement-independent, with physical location in separate columns |
| Ordered groups | Normalised child rows with an explicit ordinal. No arrays, lists or delimited strings |
| Migration | A written note and re-registration. No migration scripts |
| Release | One bump to 2.0.0 covering 1.1.0's content and B |

## Boundaries

- The module list stays at six. The release bundle has no design document under `design/modules/`, no
  directory under `implementation/{platform}/modules/`, no container, placement or grants. No product
  deploys it. It lives in `release/`, generated by `tooling/release/`.
- The deployed declaration is a relation owned by Semantic, alongside `DataProductRegistry`.
- The renderer refuses to write output into reserved directories.

## Identity grammar

| Kind | Form | Example |
|---|---|---|
| Entity | `module.entity` | `domain.ticket` |
| Entity surface | `module.entity:surface`, surface `base`, `governed`, `current` or `history` | `domain.ticket:current` |
| Module-owned object that is not an entity | `module:object` | `observability:trust_map` |
| Composite access object | `composite:name` | `composite:ticket_enriched` |

`module` is the module anchor; `entity` and `object` are the logical name in snake_case
(`ValidationRun` becomes `validation_run`). An identity contains no container, product prefix or
object-type affix, so it does not change when a container is renamed or the design is deployed with
different placement. The surface follows the object role: table `base`, base view `governed`, consumer
view `current`, point-in-time function or procedure `history`.

Physical location stays in its own columns: `container_name` and `table_name` on `EntityMetadata`;
`container_name` and `object_name` on `AccessObject`, `PrimaryObject` and `DataProductOrientation`.

## Metadata model

All relations are `CURRENT_STATE` and use the design's own style: a generated `Identifier` first
attribute, and a `Reference` to a parent where one row belongs to another.

| Relation | Status | Content |
|---|---|---|
| `EntityMetadata` | changed | `entity_name` is the logical identity (`logical_name` keeps the specification's name). `surrogate_key_column` and `natural_key_column` are removed |
| `KeyDefinition` | new | `entity_id` (reference), `key_role` (`SURROGATE`, `NATURAL`, `ALTERNATE`), `key_name` |
| `KeyColumn` | new | `key_definition_id` (reference), `ordinal`, `column_name` |
| `TableRelationship` | changed | `relationship_name`, `source_entity` and `target_entity` (logical identities), type, cardinality, mandatory. The container, table and column attributes are removed |
| `RelationshipColumn` | new | `relationship_id` (reference), `ordinal`, `source_column`, `target_column` |
| `AccessObject` | changed | Adds `object_identity`, the logical identity. `represents_entity` and `resolves_to_object` use logical identities |
| `AccessComposition` | changed | `join_path` is replaced by `via_relationship_id` and `via_direction` |
| `AccessColumn` | new | `access_object_id` (reference), `ordinal`, `column_name`, `source_entity`, `source_column`, `mapping_kind` (`PASSTHROUGH`, `RENAMED`, `DERIVED`), `derivation_note` |
| `StandardDeclaration` | new | `product_id`, `component_kind` (`STANDARD`, `MODULE`, `PATTERN`), `component_name`, `platform`, `standard_version` |

A composite natural key is the ordered rows of its `KeyColumn`. The specification language already lets an
entity declare several attributes as its natural key; 1.x collapsed them into one comma-joined string. An
entity has a `SURROGATE` key where one is allocated and otherwise its `NATURAL` key.

A reference carries one source column, so a relationship pairs it with the first column of the target's
identity. Any further column of a composite target identity is reported as a gap, never dropped.

### Access surface

`RelationshipPaths` has one row per path step and key position, with these columns in this order:

| Column | Meaning |
|---|---|
| `path_id` | The ordered legs of the path: each a relationship id followed by `>` for FORWARD or `<` for REVERSE, for example `12>7<` |
| `origin_entity`, `destination_entity` | The entities the whole path starts from and ends at |
| `hop_count` | Number of steps in the path |
| `hop` | Position of the step in the path, from 1 |
| `key_ordinal` | Position of the column pair within the join group |
| `from_entity`, `from_column`, `to_entity`, `to_column` | One pair of the join |
| `relationship_id`, `direction` | The relationship the step traverses and the way it is crossed |

Paths are bounded to four hops and visit no entity twice. The concatenated `join_path` string is gone on
every platform. `DataProductManifest` gains `standard_version` as its last column.

Consumer views take their columns from one list in the build context (`view_columns`), so a view and its
`AccessColumn` rows cannot drift.

## Conformance checks

Declared by each binding as `contract` checks and a `product` check, zero rows meaning a pass:

| Check | Invariant | Rule |
|---|---|---|
| `contract identity` | `INV-SEMANTIC-016` | Every entity and access identity follows the grammar; an entity's qualifier is its own module; entity identities are unique |
| `contract keys` | `INV-SEMANTIC-017` | Every entity has a key; key columns are ordered 1..n and exist on the entity |
| `contract relationships` | `INV-SEMANTIC-018` | Every relationship has at least one column pair; pairs are ordered 1..n and exist on their entities |
| `contract access-columns` | `INV-SEMANTIC-019` | Every consumer view over a registered entity has exactly one mapping row per output column, and every non-derived source exists |
| `contract composition` | `INV-SEMANTIC-020` | A composite has exactly one anchor, members ordered 1..n, and each other member joins to a prior member through a registered relationship |
| `product comment-coverage` | `MetadataCoverageCheck` | Every container, table, view, routine and column the product owns carries a comment |

## Release and documentation

- `VERSION` is `2.0.0`. `release/v2.0.0/` is generated from the resolved reference product and the bindings'
  declarations; `release/COMPATIBILITY.md` and `release/migrations/v2.0.0.md` are authored. A test fails if
  the committed bundle is stale or the migration note or compatibility row is missing.
- The migration note gives the old-to-new identity rule, the steps a deployment takes and the execution
  evidence per platform. A 1.x deployment re-registers; no script converts it.
- The design, the platform READMEs and the generated conformance reports change in step with the code.

## Testing

- Resolver and schema: the build-context tests pass with the new fields.
- DuckDB: the reference products deploy and every rendered check runs, with a test for each of the five
  contract checks breaking and for the comment-coverage check, a composite natural key, a composite join,
  the access-column mappings and the declaration.
- Postgres: the templates render and share the registration with DuckDB. The same engine tests run when
  `POSTGRES_TEST_DSN` is set; they were not run here.
- Teradata: the templates render under strict undefined variables and pass the validation suite. Execution
  is on the user's live system.

## Out of scope

- Domain key allocation, keymaps and multi-column physical keys.
- Composite access objects, which no binding renders.
- Automated migration of existing deployments.
- Tagging or publishing 2.0.0.
- Machine verification that a declaration is true; the trust map remains the evidence.

## Risks

- Teradata cannot be executed here. Its DDL, views and checks are verified only by rendering until the live run.
- The standard relations' attributes carry no description in the resolved context, so the bundle points to the
  design for column meanings rather than copying them.
- The breaking change is large for a standard with one tag. The release index and migration note state it plainly.
